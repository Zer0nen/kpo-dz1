# ВышКат — ДЗ-1 по КПО

Консольное приложение на Go для учёта транспорта и вещей. Позволяет принять транспорт после техосмотра, получить отчёт по инвентарю и энергопотреблению, найти транспорт для новичков. Данные хранятся в памяти до завершения программы.

## Запуск

Требуется Go 1.27.1 или новее. Все команды выполняются из папки `DZ1`. Внешних зависимостей нет.

```sh
go run .
```

Сборка для Windows:

```sh
go build -o bin/vyshkat.exe .
```

## Команды

| Команда | Действие |
| --- | --- |
| `scooter <простота> <исправен>` | Добавить обычный самокат |
| `bicycle <простота> <исправен>` | Добавить велосипед |
| `electric-scooter <простота> <исправен> <энергия>` | Добавить электросамокат |
| `electric-bicycle <простота> <исправен> <энергия>` | Добавить электровелосипед |
| `helmet` | Добавить шлем |
| `station <энергия>` | Добавить зарядную станцию |
| `dock <энергия>` | Добавить док-станцию |
| `cabinet <энергия>` | Добавить зарядный шкаф |
| `report` | Показать количество транспорта и вещей, общий расход энергии, названия и номера всех объектов |
| `beginners` | Показать транспорт для новичков с номером, названием и простотой |
| `help` | Показать справку |
| `exit` | Завершить работу |

Простота — целое число от 1 до 10; для новичков подходит транспорт со значением ≥ 6. Исправность задаётся как `true` или `false`: сервисный центр принимает исправный транспорт и отклоняет неисправный. Вещи проходят регистрацию без техосмотра.

Энергия задаётся в кВт·ч за сутки, дробная часть отделяется точкой. Допускается ноль; отрицательные значения, `NaN` и бесконечность отклоняются. Для станций, док-станций и шкафов указывается собственное потребление, без повторного включения расхода транспорта. У обычного самоката, велосипеда и шлема свойства энергопотребления нет.

Инвентарные номера общие для транспорта и вещей, назначаются автоматически с 1 после успешного приёма. Отказ не занимает номер и не меняет парк. При ошибке команды приложение выводит причину и продолжает работу.

## Пример работы

После `go run .` можно последовательно ввести:

```text
report
beginners
scooter 7 true
bicycle 5 true
electric-scooter 6 true 1.5
electric-bicycle 8 true 2
helmet
station 0.5
dock 0.25
cabinet 0.75
electric-bicycle 8 false 1
scooter 11 true
report
beginners
help
exit
```

Первые два запроса показывают пустой парк. Затем восемь объектов получают номера 1–8. Неисправный электровелосипед отклоняется техосмотром, а самокат с простотой 11 — проверкой входных данных.

Итог: **4 транспортных средства, 4 вещи, 5 кВт·ч за сутки**. Новичкам подходят самокат № 1, электросамокат № 3 и электровелосипед № 4. Велосипед № 2 с простотой 5 в этот список не попадает.

## Устройство проекта

| Файл | Назначение |
| --- | --- |
| [main.go](main.go) | Запуск и небольшой DI-контейнер `Container` |
| [console.go](console.go) | Чтение команд, создание моделей и вывод результатов |
| [park/models.go](park/models.go) | Интерфейсы, конкретные типы и конструкторы с проверками |
| [park/fleet.go](park/fleet.go) | Учёт `Fleet`, интерфейс `Inspector` и реализация `ServiceCenter` |
| [park/fleet_test.go](park/fleet_test.go) | Тесты моделей, учёта, техосмотра и отбора новичков |
| [console_test.go](console_test.go) | Тесты консольных сценариев и повторного получения парка из контейнера |

`InventoryItem` объединяет объекты с названием и инвентарным номером, `Transport` добавляет характеристики транспорта, `EnergyConsumer` описывает потребление энергии. Общие данные и методы переиспользуются через встраивание `asset`, `vehicle` и `energyUsage`. Это композиция структур Go, без наследования классов.

Поля моделей закрыты; объекты создаются конструкторами. Номер назначает `Fleet`, публичного метода изменения номера нет. Из-за закрытого метода `assignInventoryNumber` новые самостоятельные реализации `InventoryItem` добавляются внутри пакета `park`.

## SOLID, KISS и YAGNI

| Принцип | Применение |
| --- | --- |
| **SRP** | `Console` отвечает за взаимодействие, `Fleet` — за учёт и отчёты, `ServiceCenter` — за решение техосмотра. Изменение формата команды не затрагивает правила приёмки. |
| **OCP** | `Fleet` работает с интерфейсами: новый вид транспорта участвует в учёте и отчётах без изменения их алгоритмов. В консоли принцип сознательно ограничен: для нового типа нужна ветка выбора конструктора и строка справки. |
| **LSP** | Все виды транспорта соблюдают один контракт: предоставляют название, номер, простоту и исправность. `Fleet` и инспектор используют их одинаково; общие сценарии проверяются для всех четырёх типов. |
| **ISP** | Энергопотребление выделено в отдельный интерфейс. Обычный велосипед и шлем не реализуют ненужный метод расхода энергии. |
| **DIP** | `Fleet` зависит от `Inspector`, получаемого через конструктор, а не создаёт `ServiceCenter` самостоятельно. В тестах используется подмена инспектора. |

Наиболее явно применён **DIP**: подмена `Inspector` действительно меняет решение о приёмке в `TestInspectorDecision`. `Container` в `main.go` лениво создаёт и сохраняет инспектора и парк; повторные обращения возвращают уже созданные зависимости. Контейнер используется при запуске, бизнес-логика к нему не обращается.

Ограничение OCP в консоли приемлемо для небольшого приложения с фиксированным набором команд: явный `switch` легко прочитать и изменить. Отдельная система регистрации команд усложнила бы решение. `Console` также получает конкретный `*park.Fleet`: дополнительный интерфейс для него пока не нужен.

**KISS и YAGNI:** два пакета, хранение в одном срезе, небольшой типизированный контейнер. Общие структуры используются несколькими реальными типами. Разделение на дополнительные слои и функции вне задания не вводится.

## Что изменится при расширении

- **Новый транспорт:** добавить тип и конструктор в `park`, реализовать `Transport`, при необходимости — `EnergyConsumer`, добавить команду и тесты. Учёт, суммирование энергии и отбор новичков останутся прежними, если сохраняются текущие правила.
- **Сотрудники:** завести отдельную модель и учёт сотрудников. Они не реализуют `InventoryItem` и не попадают на баланс вещей; существующий `Fleet` менять не требуется.
- **Склад запчастей:** добавить модель остатков и операции прихода/расхода с отдельными командами. Для инвентаризуемого оборудования склада можно использовать `InventoryItem`. Приёмка транспорта и текущие отчёты парка сохранятся.

## Тесты

```sh
go test -count=1 "-coverpkg=./..." "-coverprofile=coverage.out" ./...
go tool cover "-func=coverage.out"
go tool cover "-html=coverage.out" -o coverage.html
```

Последний замер общего покрытия инструкций — **97,3%**. Текущий результат можно получить командами выше.

Ключевые проверки:

- `TestInspectorDecision` — подмена через `NewFleet(&fixedInspector{...})`. Проверяются принятие и отказ для каждого вида транспорта независимо от его исправности: решение принимает внедрённый инспектор. При отказе сохраняются состав парка, номера и причина ошибки.
- `TestBeginnerBoundary` — простота 5 исключает транспорт из списка новичков, 6 включает; проверяются все четыре вида.
- `TestConstructors` — допустимые характеристики, границы простоты и некорректный расход энергии.
- `TestFleet` — регистрация всех восьми типов, общий расход, номера, запрет повторного добавления и отказ неисправному транспорту.
- `TestEnergyOverflowDoesNotChangeFleet` — переполнение суммы энергии не меняет парк и не занимает номер.
- `TestConsole`, `TestInvalidConsoleInput`, `TestConsoleRejectsEveryBrokenTransport` — полный сценарий, ошибки ввода и отказ каждому неисправному виду транспорта через консоль.
